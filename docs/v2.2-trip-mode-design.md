# V2.2 — Trip / dashcam mode (design)

_Status: specced, not built. Endorsed 2026-08-23. Depends on: V2.0 (done). See
[PROJECT-STATUS](PROJECT-STATUS.md)._

## Goal

Open the app, start recording a trip (drive or walk), and have it **auto-tag potholes and
garbage dumps along the route** — each tagged issue pinned to where on the GPS track it was
seen. This is the "many citizen sources" vision applied to continuous capture; dashcam is
already a first-class source in the architecture plan.

## Flow

1. Record video **+ a timestamped GPS track** (the phone provides both).
2. **Sample frames** (~1 fps).
3. **Frame-dedup gate** (`pipeline/frames.py`, perceptual dHash) drops near-identical frames —
   this is what makes video affordable (collapsed 190 frames → 3 detector calls in testing).
4. **Assign each surviving frame a coordinate** by interpolating the GPS track at the frame's
   timestamp — *the one genuinely new piece*.
5. Detector on the survivors → **10 m geo-dedup** → issues on the map (pass a pothole once →
   one issue; drive the same road twice → 10 m merge).

## What already exists

- `pipeline/frames.py` — dHash frame-dedup gate (built for exactly this).
- `Report(source="dashcam")` is a first-class source in the data model.
- Detector + 10 m geo-dedup + issue lifecycle + the `POST /v1/reports` contract.

## What's missing

- **Video-ingestion path:** accept a video + GPS track, sample frames, per-frame geotag, batch
  into reports.
- **Frame ↔ location time-sync / interpolation.**
- **On-device "record" UI** (capture + optional pre-filter).

## Key design forks (resolve at plan time)

- **Batch vs. live.** With a cloud VLM (~25 s/image) tagging is **batch**: record now, issues
  populate minutes later. Near-real-time needs an **on-device small model** (bigger lift).
  Recommendation: ship **batch first**; treat on-device-live as a later increment.
- **On-device pre-filter vs. upload-everything.** Sampling + dHash dedup **on the phone**,
  uploading only candidate frames, slashes bandwidth/battery *and* VLM footprint. Recommended
  over uploading whole videos. Upload-and-process server-side is the simpler v0.
- **Geotag interpolation:** nearest-sample vs. linear interpolation between GPS fixes; how to
  handle gaps / low-signal stretches (dashcams often run where signal is poor).

## Honest caveats (set expectations, design around)

- **Detection quality drops at speed** — motion blur, oblique angles, potholes small in frame.
  A deliberate photo detects far better than a 50 km/h frame grab.
- **Privacy becomes mandatory** — continuous public-street video sweeps up faces/plates; the
  blur gate (see [V2.1](v2.1-citizen-view-design.md)) is not optional here.
- **Battery / thermal / storage** — continuous capture + upload is heavy; favors on-device
  pre-filter.

## Suggested task shape (for the eventual plan)

1. Video-ingest endpoint: accept `video` + `gps_track` (list of `{t, lat, lng}`); sample →
   dHash dedup → per-frame geotag interpolation → enqueue as reports (`source="dashcam"`).
2. Reuse the existing worker → detector → 10 m dedup unchanged.
3. On-device capture UI: record video + track; (v1) upload; (v2) on-device sample+dedup, upload
   candidate frames only.
4. Tie in the privacy blur gate before any public surface.

Reuses the whole existing pipeline after step 1 — the new surface area is ingestion + capture,
not detection or dedup.
