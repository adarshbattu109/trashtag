# V2.1 — Citizen-facing report view (design)

_Status: specced, not built. Decided 2026-08-23. Depends on: V2.0 (done). See
[PROJECT-STATUS](PROJECT-STATUS.md)._

> **Bundled into this release:** the `fastapi-mcp` → `fastmcp` migration (lifting the `mcp<2`
> pin) — see [§ Companion work](#companion-work-lift-the-mcp2-pin-fastapi-mcp--fastmcp) below.
> It's grouped here because V2.1 is the first release that opens a public/citizen surface, so we
> want the MCP server on the current, maintained, spec-compliant stack before that exposure —
> and it clears the standing Dependabot noise on `mcp`.

## Goal

Let the person who submitted a report see what happened to it: their **actual submitted
photo**, what was detected (class / confidence / severity), and the issue's **lifecycle
status** (new → verified → filed → in_progress → resolved). Today everything is ops-internal
(the reviewer dashboard); a submitter has no view of their own.

## Core decision — single portal, not a separate app

**Everyone uses the same portal (the existing dashboard). The admin/reviewer just gets the
extra "review option"** (Verify / Reject / Merge / severity edit) that a regular user does not
see. Do **not** build a separate citizen app.

Consequence: build the full-featured dashboard now (V2.0 already did); when auth lands,
**role-gate the review controls** so non-admins see a read-only view. The data surface is the
same for both.

## What already exists (V2.0)

- Real submitted photo: `GET /v1/issues/{id}/evidence` (+ `?w=` thumbnail).
- Detection fields (class/confidence/severity) and live status on the issue record from
  `GET /v1/issues` and `GET /v1/issues/{id}`.
- The dashboard renders all of the above.

## What's missing

1. **A way for a citizen to reach their report.** Either a per-report **shareable read-only
   link** (no auth) or a **"my reports" list** (needs auth to know *whose*).
2. **Role gating.** Hide Verify/Reject/Merge/severity for non-admins. Needs auth/RBAC (§5d in
   the [V2 spec](v2-design-spec.md)), which is deferred.
3. **The privacy / blur gate.** A citizen-reachable page is effectively *public*. Evidence
   photos must pass a **face / licence-plate blur** step before public exposure (a hard
   project principle). Ops-internal use skips this; a citizen view cannot.

## Open decisions (resolve before/at plan time)

- **Reach mechanism:** shareable per-report link (ships without auth, fastest) **vs.** a
  "my reports" list (blocked on auth). Recommendation: start with the **read-only shareable
  link** so the feature isn't blocked on the auth task; add "my reports" when auth exists.
- **Blur gate implementation:** where it runs (on the evidence endpoint when serving to a
  public/shared context vs. a one-time processing step at ingest), and which model
  (on-device / server-side). This is a prerequisite, not optional.
- **What a shared link exposes:** photo + status + class only? Hide precise GPS on the public
  view (show ward/area) for the submitter's privacy?
- **Link security:** unguessable token per report vs. issue id; expiry?

## Companion work: lift the `mcp<2` pin (fastapi-mcp → fastmcp)

Folded into V2.1. Full analysis: [`docs/research/mcp-2x-upgrade-path.md`](research/mcp-2x-upgrade-path.md).

- **Why now:** V2.1 opens the first public/citizen surface, so the MCP server should be on the
  current, maintained, mcp-2.x-compliant stack before that exposure. `fastapi-mcp` is effectively
  unmaintained (no release since Jul 2025; open issues #321/#323 confirm no mcp-2.x support), which
  is why we currently pin `mcp<2`. Bundling the swap here also clears the recurring Dependabot noise.
- **What changes:** in `src/trashtag/app/serve.py`, replace `FastApiMCP(app); mcp.mount_http()` with
  `FastMCP.from_fastapi(app=app)` mounted via `http_app("/mcp")`, combining its lifespan with our
  existing worker lifespan (`combine_lifespans`). Swap `fastapi-mcp` + the `mcp<2` cap for `fastmcp`
  in `pyproject.toml`; add `fastapi` as an explicit dep if not already. Effort: low-to-medium, ~1 file.
- **Verify:** `uv sync` resolves mcp 2.x with no `<2` cap; `uv run python -c "from trashtag.app.serve import app"`
  imports clean (the old crash path); `/mcp` responds and exposes the same tool set reviewers/agents expect.
- **Independence:** this has no dependency on the citizen-view work — it can land as its own task/PR
  first within the V2.1 branch, de-risking the release.

## Suggested task shape (for the eventual plan)

1. **Lift the `mcp<2` pin** — migrate `fastapi-mcp` → `fastmcp` (per § Companion work). Independent;
   do it first to clear the pin and Dependabot noise.
2. Blur-gate spike + a `blurred_evidence` path (or on-serve blur) — the gating prerequisite.
3. Public read-only route: `GET /r/{token}` → a minimal status page (blurred photo + status +
   class), no review controls, no precise GPS.
4. Return/store a per-report share token at ingest; surface it in the submit confirmation.
5. (After auth) role-gate the dashboard review controls; add "my reports".

Do **not** fold this into a V2.0-style branch until the blur gate is decided — it's the
load-bearing dependency.
